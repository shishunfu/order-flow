# EXP-025：异步调用超时预算传播与任务取消

## 1. 实验目标

验证异步调用中的整体 Deadline、下游剩余时间传播、任务中断、资源清理和线程池恢复能力。

重点回答：

- 多个下游如何共享整体请求时间预算？
- Future 取消后，底层任务是否真正退出？
- 整体超时后，如何主动取消其他下游任务？
- 慢任务退出后，线程池能否继续处理新任务？

## 2. 实验环境

- JDK：OpenJDK 25.0.2
- 测试框架：JUnit 5
- 并发工具：ExecutorService、Future、CountDownLatch
- 时间计算：System.nanoTime()
- 整体 Deadline：800ms（场景 A）
- 整体超时模拟：200ms（场景 C）

## 3. 实验结果

测试结果：4 个测试全部通过，0 失败，0 错误。

### A：整体 Deadline 传播

实测剩余时间：

| 阶段 | 剩余时间 |
|---|---:|
| 订单 | 599ms |
| 商品 | 448ms |
| 库存 | 348ms |

结论：

多个下游共享同一个 Deadline，随着前序耗时增加，后续下游可使用的剩余时间逐渐减少。

使用 System.nanoTime() 计算相对时间，避免系统时钟调整影响。

### B：下游任务响应中断

实测结果：

- cancel(true)：true
- interrupted：true
- resourceReleased：true
- futureCancelled：true

结论：

任务响应 InterruptedException 后，执行 finally 清理逻辑并退出。

Future 进入取消状态本身不能证明底层任务已经停止，必须结合任务退出信号验证。

### C：整体超时后取消其他下游

实测结果：

- 订单任务取消：true
- 商品任务取消：true
- 库存任务取消：true
- 三个任务均完成退出清理

结论：

整体超时后，可以主动向其他仍在运行的任务发送取消请求，避免继续无意义地占用工作线程。

### D：线程池 Worker 恢复

实测结果：

- 慢任务响应中断：true
- 后续探测任务：PROBE-SUCCESS
- 探测任务由 deadline-recovery-worker 执行

结论：

慢任务退出后，单线程 Executor 能够继续处理后续任务，验证了 Worker 恢复能力。

## 4. 核心技术结论

1. 多个下游应共享同一个整体 Deadline。
2. 下游超时时间应根据剩余预算计算，而不是重新获得完整请求预算。
3. Future.cancel(true) 发出中断请求，不保证任务一定停止。
4. 任务应主动响应中断，并在 finally 中释放资源。
5. 整体超时后，需要主动取消其他仍在执行的下游任务。
6. 慢任务及时退出，有助于恢复线程池处理能力。

## 5. 生产环境风险

如果任务忽略中断，可能出现：

- 请求已经超时，但后台任务继续执行。
- 工作线程长期被慢任务占用。
- HTTP 连接池、数据库连接池资源不能及时释放。
- 超时请求持续积累，最终导致线程池耗尽。

生产环境应结合底层客户端的连接超时、响应超时、查询超时和取消机制，不能只依赖 CompletableFuture 或 Future 的超时状态。

## 6. 实验局限

本实验验证的是 Java 线程中断协作机制，不代表真实 HTTP 或 JDBC 调用一定可以被中断。

场景 C 通过等待 Deadline 到期后主动调用 cancel(true)，尚未实现自动调度取消的生产级编排器。

场景 D 验证了同一个单线程 Executor 可以继续处理后续任务，但没有测量高并发压力下的线程池恢复速度。

此外，本实验中的 resourceReleased 是 finally 执行的验证标志，并非真实连接池或外部资源的释放证明。

## 7. 验收结果

- [x] Deadline 剩余预算逐步减少
- [x] 下游任务响应中断
- [x] finally 清理逻辑执行
- [x] 整体超时后取消其他下游
- [x] 验证取消后底层任务退出
- [x] 验证线程池可以继续执行新任务
- [x] 测试线程池正常关闭

## 8. 最终结论

异步系统的超时治理不能停留在 Future 异常完成这一层。

可靠的生产级设计需要贯通整体 Deadline、下游剩余时间、任务取消、中断响应和资源释放。

只有底层任务真正退出，线程池和外部资源才能得到有效恢复。
