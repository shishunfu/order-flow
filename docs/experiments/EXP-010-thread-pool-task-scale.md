# EXP-010：线程数与任务规模关系实验

## 1. 实验目的

研究 CPU 密集型任务在不同任务规模和 Worker 数量下的吞吐量、等待时间和总处理时间变化。

## 2. 实验环境

- JVM 可用处理器数：16
- CPU 计算次数：5,000,000 次/任务
- Worker 数：8、16、32
- 任务规模：200、1000、2000
- 每组重复次数：5
- 队列容量：任务总数
- 拒绝策略：AbortPolicy
- 测试组合：9 组，共 45 次正式测试

## 3. 实验结果

| 任务数 | Worker | 吞吐量中位数 | 平均等待中位数 | 总耗时中位数 |
|---:|---:|---:|---:|---:|
| 200 | 8 | 1110.51 | 86.34ms | 180.10ms |
| 200 | 16 | 1696.44 | 52.99ms | 117.89ms |
| 200 | 32 | 1746.89 | 50.14ms | 114.49ms |
| 1000 | 8 | 1107.67 | 438.60ms | 902.80ms |
| 1000 | 16 | 1822.70 | 266.32ms | 548.64ms |
| 1000 | 32 | 1812.82 | 268.34ms | 551.63ms |
| 2000 | 8 | 1147.82 | 846.05ms | 1742.43ms |
| 2000 | 16 | 1808.86 | 548.52ms | 1105.67ms |
| 2000 | 32 | 1777.33 | 553.89ms | 1125.28ms |

吞吐量单位：tasks/s。

## 4. 关键发现

1. 在相同 Worker 数下，任务量增加时吞吐量总体保持稳定。
2. 任务规模增加会明显增加总耗时和平均等待时间。
3. 16 Worker 在 1000、2000 个任务规模下略优于 32 Worker。
4. 32 Worker 没有体现出稳定、显著的额外吞吐量收益。
5. 增加 Worker 可能增加单任务执行时间，说明并发度提高不一定等于执行效率提高。

## 5. 工程结论

CPU 密集型任务的线程池容量不能简单根据任务总量确定。

任务规模主要影响排队时间和整体完成时间，而线程池的持续处理能力还受到 CPU 资源、任务计算量和线程调度开销限制。

对于本次实验环境和任务模型，16 Worker 是值得优先考虑的测试起点；32 Worker 没有表现出稳定的额外收益。

这不是生产环境的最终参数，应结合真实业务负载和 CPU 利用率继续验证。

## 6. 实验局限

- 预热发生在测试线程，而不是各 Worker 线程。
- 未采集 CPU 利用率、上下文切换和 CPU 频率。
- 测试任务为模拟 CPU 计算，不代表所有真实业务。
- 测试过程中可能受到 JVM JIT 和操作系统调度影响。
- 平均等待时间包含提交期间经过的时间，不等于严格的队列驻留时间。

## 7. 后续方向

进一步研究有界队列容量、任务拒绝和过载保护之间的关系，理解线程池如何在高负载下保护系统。
