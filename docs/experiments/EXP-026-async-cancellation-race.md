# EXP-026：异步任务取消传播与并发竞态

## 1. 实验目标

验证多个异步任务同时完成、超时或被取消时的状态管理和资源清理行为。

重点研究：

- 已完成任务是否会被误取消。
- 多个线程重复取消同一个任务时，清理逻辑是否重复执行。
- Future 正常完成与取消并发竞争时，最终状态是否一致。
- 多个下游部分成功后发生整体失败，如何保留成功结果并取消剩余任务。

## 2. 实验场景与结果

测试结果：4 个测试全部通过，0 失败，0 错误。

### A：已完成任务与未完成任务的取消

实测结果：

- ORDER-SUCCESS 成功返回。
- 已完成任务 cancelled=false。
- 慢任务 cancelled=true。
- 慢任务 finally 正常执行。

结论：取消传播应针对仍有必要取消的任务，不能无差别取消所有 Future。

### B：并发重复取消

实验使用 8 个线程同时调用同一个 Future 的 cancel(true)。

实测结果：

- Future cancelled=true。
- cleanupCount=1。

结论：多个线程可以重复调用 Future.cancel，但单次任务执行退出时，finally 只执行一次。

生产系统中的外部资源关闭、业务补偿和状态更新仍然需要独立的幂等保护。

### C：任务完成与取消竞争

实验循环 100 次，让任务正常完成和取消操作并发竞争。

实测结果：

- 最后一次竞争结果：SUCCESS。
- cleanupCount=100。
- 100 次测试全部通过。

结论：Future 最终只能处于正常完成或取消状态之一。

正常完成时可以取得结果；取消完成时 get() 抛出 CancellationException。

注意：本实验没有统计 100 次竞争中 SUCCESS 和 CANCELLED 各自出现的次数，因此不能据此判断竞争胜率。

### D：部分成功与整体失败

实测结果：

- ORDER-1001 保留。
- PRODUCT-2001 保留。
- 库存 Future cancelled=true。
- 库存任务 finally 正常执行。

结论：已经成功取得的下游结果可以保留，仍在执行的任务可以按整体失败策略取消。

## 3. 核心技术结论

1. 已完成任务不需要再次取消，应保留其结果。
2. Future.cancel 可以被多个线程重复调用。
3. finally 可以用于单次任务执行的清理，但不能代替所有外部资源的幂等保护。
4. Future 的完成和取消存在竞争，最终状态必须通过 Future 本身判断。
5. 部分成功与整体失败需要分开管理：保留已有结果，取消不再需要的任务。
6. 取消请求成功不等于底层任务一定已经停止，仍需验证任务退出和资源清理。

## 4. 实验局限与风险

场景 C 没有对任务开始执行设置单独的同步屏障，因此存在任务可能在开始执行前就被取消的调度可能性。

当前实现通过 taskFinished 闸门验证退出，但如果任务在执行前被取消，Callable 不会运行，闸门也不会由 Callable 释放。

本次运行通过了，但建议后续优化该测试的同步设计，避免依赖线程调度时机。

此外，本实验只验证 Java Future 和线程中断机制，不代表真实 HTTP、JDBC 或消息调用的取消行为。

## 5. 验收结果

- [x] 已完成任务不被误取消
- [x] 并发重复取消时清理只执行一次
- [x] 100 次完成/取消竞争均通过
- [x] Future 最终状态判断正确
- [x] 部分成功结果得到保留
- [x] 剩余任务能够被取消
- [x] 测试线程池正常关闭

## 6. 最终结论

异步任务生命周期管理不仅要关注任务能否完成，还需要处理任务完成、异常、超时和取消之间的并发竞争。

生产级异步编排需要明确任务状态、取消边界、清理责任和幂等机制，避免取消传播误伤已经完成的任务，也避免资源清理和业务补偿被重复执行。
