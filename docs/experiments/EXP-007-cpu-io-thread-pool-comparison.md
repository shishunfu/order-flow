# EXP-007：CPU 密集型与 I/O 等待型任务的线程池对比实验

## 1. 实验目标

比较 CPU 密集型任务与 I/O 等待型任务在线程池中的运行表现，理解不同任务类型对线程数的需求差异。

重点观察：

- 线程数变化对吞吐量的影响；
- 线程数变化对任务等待时间的影响；
- 线程数变化对任务执行时间的影响；
- CPU 密集型和 I/O 等待型任务的并发特征。

## 2. 实验环境与参数

| 参数 | 配置 |
|---|---:|
| 任务总数 | 40 |
| 队列容量 | 40 |
| 拒绝策略 | AbortPolicy |
| CPU 任务计算次数 | 5,000,000 次循环 |
| I/O 模拟等待 | 200ms |
| 线程数 | 1、2、4、8 |
| CPU 预热 | 10 次计算 |

CPU 任务通过数值计算模拟，I/O 等待型任务通过 `Thread.sleep(200)` 模拟。

注意：`Thread.sleep()` 不是实际网络或磁盘 I/O，仅用于模拟线程等待行为。

## 3. CPU 密集型实验结果

| 线程数 | 平均执行时间 | 平均等待时间 | 最大等待时间 | 总耗时 | 吞吐量 |
|---:|---:|---:|---:|---:|---:|
| 1 | 6.57ms | 127.87ms | 255.03ms | 265ms | 150.94 tasks/s |
| 2 | 6.11ms | 58.44ms | 116.54ms | 122ms | 327.87 tasks/s |
| 4 | 6.23ms | 27.57ms | 56.20ms | 65ms | 615.38 tasks/s |
| 8 | 7.23ms | 14.92ms | 31.56ms | 39ms | 1025.64 tasks/s |

分析：

1. 线程数从 1 增加到 8，实测吞吐量持续提高。
2. 任务平均等待时间随着线程数增加而下降。
3. 线程数为 8 时，平均执行时间略有上升。
4. 本次测试没有直接采集 CPU 使用率和上下文切换数据。
5. 测试总耗时较短，JIT、调度和系统负载可能影响测量结果。

结论：

本次实验观察到增加线程数带来的吞吐量收益，但尚未测出 CPU 密集型任务的最佳线程数，也不能据此推断线程数可以无限增加。

## 4. I/O 等待型实验结果

| 线程数 | 平均执行时间 | 平均等待时间 | 最大等待时间 | 总耗时 | 吞吐量 |
|---:|---:|---:|---:|---:|---:|
| 1 | 200.65ms | 3913.77ms | 7827.65ms | 8027ms | 4.98 tasks/s |
| 2 | 200.75ms | 1906.86ms | 3815.51ms | 4016ms | 9.96 tasks/s |
| 4 | 200.73ms | 902.95ms | 1807.22ms | 2008ms | 19.92 tasks/s |
| 8 | 200.56ms | 401.40ms | 802.62ms | 1003ms | 39.88 tasks/s |

分析：

1. 单任务执行时间基本稳定在 200ms。
2. 线程数从 1 增加到 8，吞吐量近似线性增长。
3. 平均等待时间明显下降。
4. 结果与理想化模型接近：

```text
吞吐量 ≈ 并发线程数 / 单任务等待时间
```

结论：

对于本次模拟的等待型任务，增加线程数可以提高并发等待能力，从而提高吞吐量。

但真实 I/O 任务还受数据库连接池、HTTP 连接池、网络和远程服务处理能力限制。

## 5. 两种任务类型对比

| 对比项 | CPU 密集型 | I/O 等待型 |
|---|---|---|
| 主要瓶颈 | CPU 计算能力 | 外部资源等待 |
| 线程运行特征 | 持续计算 | 经常等待 |
| 增加线程数 | 可能遇到 CPU 上限 | 通常能提高并发等待能力 |
| 线程过多风险 | 上下文切换、调度开销 | 内存和下游资源压力 |
| 参数设计依据 | CPU 可用核心数及压测 | 等待时间及下游容量 |

## 6. 工程实践结论

1. CPU 密集型任务应从接近可用 CPU 核心数的线程配置开始测试。
2. I/O 等待型任务可以考虑比 CPU 核心数更多的并发线程，但必须考虑下游容量。
3. 不同业务任务具有不同资源瓶颈，不宜无条件共用同一个线程池。
4. 线程池隔离可以降低任务之间的相互影响，但不能自动隔离数据库连接、HTTP 连接和 CPU 等共享资源。
5. 线程数不能仅靠经验公式确定，需要通过压测观察吞吐量、延迟和资源利用率。
6. 本实验的 CPU 任务总耗时较短，不能直接用于确定生产环境的最佳线程数。

## 7. 对 OrderFlow 的设计启示

未来可以按任务类型规划线程池：

```text
OrderFlow
    |
    +-- CPU 计算线程池
    |      +-- 金额计算
    |      +-- 规则计算
    |      +-- 数据转换
    |
    +-- I/O 线程池
    |      +-- 外部服务调用
    |      +-- 异步查询
    |      +-- 文件读写
    |
    +-- 批处理线程池
           +-- 批量导入
           +-- 报表生成
```

线程池隔离应结合数据库连接池、HTTP 连接池和业务优先级一起设计。
