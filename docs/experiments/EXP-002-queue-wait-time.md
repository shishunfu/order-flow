# EXP-002：队列容量与任务等待时间实验

## 1. 实验目的

研究线程池队列容量对任务等待时间、任务接收数量、拒绝数量的影响。

重点验证：

1. 队列容量是否会影响任务排队等待时间。
2. 增大队列容量是否能够提升线程池吞吐量。
3. 为什么队列容量增加后，任务等待时间可能反而增加。
4. 如何结合平均等待时间、最大等待时间和拒绝数量评估线程池运行状态。

## 2. 实验环境

| 项目 | 配置 |
|---|---|
| JDK | OpenJDK 25.0.2 |
| Maven | 3.9.12 |
| 核心线程数 | 2 |
| 最大线程数 | 2 |
| 任务总数 | 10 |
| 单任务模拟执行时间 | 500 ms |
| 工作队列 | ArrayBlockingQueue |
| 拒绝策略 | AbortPolicy |
| 队列容量 | 3、8、20 |

## 3. 实验指标

- 任务等待时间：任务开始执行时间 - 任务提交时间。
- 任务执行时间：任务结束时间 - 实际业务执行开始时间。
- 平均等待时间：所有完成任务等待时间的平均值。
- 最大等待时间：所有完成任务中最大的等待时间。
- 平均执行时间：所有完成任务执行时间的平均值。
- 拒绝任务数：被线程池拒绝的任务数量。

## 4. 实验结果

### 4.1 三组实验数据

| 指标 | 队列容量 3 | 队列容量 8 | 队列容量 20 |
|---|---:|---:|---:|
| 提交任务数 | 10 | 10 | 10 |
| 线程池大小 | 2 | 2 | 2 |
| 活跃线程数 | 2 | 2 | 2 |
| 实际排队任务数 | 3 | 8 | 8 |
| 拒绝任务数 | 5 | 0 | 0 |
| 实际完成任务数 | 5 | 10 | 10 |
| 平均等待时间 | 405.52 ms | 1004.82 ms | 1002.33 ms |
| 最大等待时间 | 1008.80 ms | 2007.23 ms | 2003.74 ms |
| 平均执行时间 | 500.47 ms | 500.67 ms | 500.72 ms |

### 4.2 队列容量为 3

实验结果：

- 两个工作线程处于忙碌状态。
- 三个任务进入队列。
- 五个任务被拒绝。
- 最终完成五个任务。
- 平均等待时间为 405.52 ms。
- 最大等待时间为 1008.80 ms。

分析：

队列容量为 3 时，线程池总共只能接收五个任务，即两个正在执行的任务和三个排队任务。

平均等待时间较低，是因为后五个任务被拒绝，没有进入等待时间统计。

因此，不能单纯认为队列容量为 3 的性能优于其他配置。

### 4.3 队列容量为 8

实验结果：

- 两个工作线程处于忙碌状态。
- 八个任务进入队列。
- 没有任务被拒绝。
- 最终完成十个任务。
- 平均等待时间为 1004.82 ms。
- 最大等待时间为 2007.23 ms。
- 平均执行时间为 500.67 ms。

分析：

所有任务都被线程池接收，但由于工作线程只有两个，任务必须分批执行。

任务等待时间呈现明显的批次规律：

| 任务批次 | 任务编号 | 平均等待时间 |
|---|---|---:|
| 第一批 | 1、2 | 约 0 ms |
| 第二批 | 3、4 | 约 500 ms |
| 第三批 | 5、6 | 约 1000 ms |
| 第四批 | 7、8 | 约 1500 ms |
| 第五批 | 9、10 | 约 2000 ms |

这验证了任务等待时间与前面任务执行时间、工作线程数量之间的关系。

### 4.4 队列容量为 20

实验结果：

- 两个工作线程处于忙碌状态。
- 八个任务进入队列。
- 队列仍有十二个剩余槽位。
- 没有任务被拒绝。
- 最终完成十个任务。
- 平均等待时间为 1002.33 ms。
- 最大等待时间为 2003.74 ms。
- 平均执行时间为 500.72 ms。

分析：

虽然队列容量从 8 增加到 20，但本次实验总共只有十个任务，其中两个由工作线程执行，只有八个进入队列。

因此，增加的十二个队列槽位没有被使用。

容量 20 与容量 8 的等待时间几乎相同，差异属于正常实验波动。

## 5. 核心数据分析

### 5.1 为什么容量 3 的平均等待时间更低？

容量 3 时只完成了五个任务，后五个任务被拒绝。

容量 8 和 20 时完成了全部十个任务，后续批次需要等待前面的任务完成。

因此，平均等待时间必须与完成数量、拒绝数量一起分析。

不能通过牺牲任务接收率来制造较低的平均等待时间，并据此判断线程池性能更好。

### 5.2 为什么容量 8 和 20 的等待时间基本相同？

两组实验的线程数、任务数量和任务执行时间相同，实际排队任务数也相同。

因此，虽然队列容量不同，但实际任务调度过程没有发生变化。

队列容量只是最大缓冲能力，不会直接增加工作线程的处理能力。

### 5.3 线程池理论处理能力

当前实验中：

- 工作线程数：2。
- 平均任务执行时间：约 500 ms。

理论处理能力：

Throughput = 2 / 0.5 = 4 tasks/s

即理论上每秒可以完成约四个任务。

如果任务到达速率持续为每秒十个：

积压增长速率 = 10 - 4 = 6 tasks/s

队列容量只能延缓队列被填满的时间，不能解决长期过载。

## 6. 实验结论

1. 队列容量决定线程池在工作线程忙碌时可以暂存多少任务。
2. 队列容量为 3 时，线程池接收五个任务，拒绝五个任务。
3. 队列容量为 8 时，线程池接收并最终完成全部十个任务。
4. 队列容量为 20 时，实际排队任务仍然只有八个，剩余容量没有被使用。
5. 容量从 8 增加到 20，没有明显降低平均等待时间或最大等待时间。
6. 工作线程数量和任务执行时间决定当前任务处理能力，增大队列容量并不能直接提升吞吐量。
7. 队列容量过大可能延长任务等待时间、增加内存占用，并将即时拒绝转变为延迟处理。
8. 线程池容量设计需要同时考虑任务到达速率、任务执行时间、可接受等待时间、拒绝处理机制和内存预算。

**最终结论：队列是流量缓冲机制，不是处理能力扩容机制。**

## 7. 工程应用思考

结合 OrderFlow 订单服务，后续增加异步任务时，需要考虑：

- 订单核心处理和非关键异步任务是否应该使用不同线程池。
- 如何监控队列长度和队列等待时间。
- 如何识别任务持续堆积。
- 队列满时是快速失败、降级、重试还是持久化。
- 是否需要为任务设置最大等待时间。
- 是否需要通过增加工作线程、优化任务执行时间或引入异步消息系统提升处理能力。

生产环境不能只根据队列容量判断线程池是否健康。

应该结合活跃线程数、队列长度、任务等待时间、任务执行时间、拒绝数量和实际吞吐量综合分析。

## 8. 实验边界

本实验通过 CountDownLatch 人为制造任务积压，验证线程池队列容量与任务等待时间之间的关系。

实验并非生产环境压力测试。

当前实验没有验证：

- 高并发请求下的实际任务到达速率。
- 数据库连接池竞争。
- 真实业务 I/O 等待。
- 线程池扩容行为。
- 长时间持续过载。
- 生产环境任务丢失和重试机制。

理论吞吐量是根据线程数和任务执行时间估算的，并非独立压测得到的实测吞吐量。
