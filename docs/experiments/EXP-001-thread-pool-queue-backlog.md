## 2. 实验目的

通过控制线程池工作线程数、阻塞任务和任务队列容量，观察任务提交速度超过线程池即时处理能力时的行为，理解：

1. `corePoolSize`、`maximumPoolSize` 对工作线程数量的约束。
2. `ArrayBlockingQueue` 的缓冲作用。
3. 队列满后 `RejectedExecutionHandler` 的触发条件。
4. `AbortPolicy` 如何拒绝无法接收的任务。
5. 队列容量变化对任务接收数量和积压规模的影响。

本实验重点是理解线程池的接收与排队机制，不用于评估真实业务吞吐量。

## 3. 实验设计

### 3.1 固定参数

| 参数 | 值 | 说明 |
|---|---:|---|
| `corePoolSize` | 2 | 核心工作线程数 |
| `maximumPoolSize` | 2 | 最大工作线程数 |
| `keepAliveTime` | 60 ms | 非核心线程空闲存活时间 |
| 工作队列 | `ArrayBlockingQueue` | 有界阻塞队列 |
| 拒绝策略 | `AbortPolicy` | 无法接收任务时抛出 `RejectedExecutionException` |
| 任务数 | 10 | 每轮计划提交的任务总数 |
| 阻塞方式 | `CountDownLatch` | 先占用两个工作线程，再提交后续任务 |

### 3.2 实验变量

- 实验 A：队列容量为 3。
- 实验 B：队列容量为 8。

### 3.3 实验步骤

1. 创建固定为 2 个工作线程的 `ThreadPoolExecutor`。
2. 提交两个任务，使两个工作线程都进入等待状态。
3. 在工作线程被占用期间，继续提交剩余任务。
4. 观察线程池大小、活跃线程数、队列长度和拒绝数量。
5. 释放 `CountDownLatch`，允许工作线程消费队列中的任务。
6. 等待线程池关闭，观察最终完成任务数量。

## 4. 实验结果



### 4.1 实验 A：队列容量为 3

用户实测控制台关键数据：

| 指标 | 实测值 |
|---|---:|
| 线程池大小 | 2 |
| 活跃线程数 | 2 |
| 队列长度 | 3 |
| 拒绝任务数 | 5 |
| 最终完成任务数 | 5 |

任务接收情况：

| 状态 | 数量 |
|---|---:|
| 正在执行（被闸门阻塞） | 2 |
| 排队等待 | 3 |
| 被拒绝 | 5 |
| 最终完成 | 5 |

结论：线程池最多接收 5 个任务，即 2 个工作线程正在处理的任务加上 3 个队列槽位。剩余 5 个任务因队列已满且线程数达到最大值，被 `AbortPolicy` 拒绝。

### 4.2 实验 B：队列容量为 8

用户实测控制台关键数据：

| 指标 | 实测值 |
|---|---:|
| 线程池大小 | 2 |
| 活跃线程数 | 2 |
| 队列长度 | 8 |
| 拒绝任务数 | 0 |
| 释放闸门前完成任务数 | 0 |
| 释放闸门并等待结束后的完成任务数 | 10 |

任务接收情况：

| 状态 | 数量 |
|---|---:|
| 正在执行（被闸门阻塞） | 2 |
| 排队等待 | 8 |
| 被拒绝 | 0 |
| 最终完成 | 10 |

结论：线程池接收了全部 10 个任务。释放闸门前，两个工作线程仍在等待，队列中的 8 个任务尚未开始执行，因此当时完成数为 0。释放闸门后，工作线程逐个消费队列任务，最终完成数为 10。

**关于两个完成数的说明：** `0` 是释放闸门之前的瞬时观测值，`10` 是释放闸门之后等待线程池结束时的最终统计值，两者处于不同观测时点，并不矛盾。

## 5. 结果对比

| 队列容量 | 工作线程数 | 排队任务数 | 拒绝任务数 | 最终完成数 |
|---:|---:|---:|---:|---:|
| 3 | 2 | 3 | 5 | 5 |
| 8 | 2 | 8 | 0 | 10 |

本实验中 `maximumPoolSize` 与 `corePoolSize` 都是 2，因此线程池不会通过增加非核心线程来处理更多任务。容量变化影响的是任务缓冲数量，而不是工作线程数量。

## 6. 原理分析

### 6.1 ThreadPoolExecutor 的任务接收顺序

在工作线程数量小于核心线程数时，线程池优先创建核心工作线程；达到核心线程数后，优先尝试将任务放入工作队列；队列无法接收任务时，才尝试创建非核心线程，直到达到 `maximumPoolSize`；如果线程数已达到最大值且队列也无法接收任务，则执行拒绝策略。

```text
                          提交任务 execute(command)
                                  │
                                  ▼
                  ┌───────────────────────────────┐
                  │   ctl 中取出 workerCount       │
                  │  (高三位是状态，低29位是线程数)│
                  └───────────────┬───────────────┘
                                  │
                                  ▼
              ┌── workerCount < corePoolSize ? ──┐
              │                                   │
            是 │                                 否
              │                                   │
              ▼                                   ▼
    ┌───────────────────┐          ┌───────────────────────────┐
    │ addWorker(command,│          │     任务能入队吗？          │
    │     true)         │          │  workQueue.offer(command)  │
    └─────────┬─────────┘          └─────────────┬─────────────┘
              │                                    │
          成功 │                               成功 │
              │                                    ▼
              ▼                           ┌─────────────────┐
         新建核心线程                      │   任务入队成功   │
         执行任务                          └─────────────────┘
              │                                    │
              │                              失败  │
              │                                    ▼
              │                      ┌─────────────────────────────┐
              │                      │ workerCount < maximumPoolSize ?│
              │                      └─────────────┬───────────────┘
              │                                是  │
              │                                    ▼
              │                          ┌───────────────────┐
              │                          │ addWorker(command,│
              │                          │     false)        │
              │                          └─────────┬─────────┘
              │                                成功 │
              │                                    ▼
              │                              新建非核心线程
              │                              执行任务
              │                                    │
              │                               失败  │
              │                                    ▼
              │                          ┌─────────────────┐
              └──────────────────────────▶  触发拒绝策略    │
              失败（创建线程失败时）       └─────────────────┘
                                    handler.rejectedExecution()
```

本实验最大线程数等于核心线程数，因此队列满后没有扩容空间，直接触发拒绝策略。

### 6.2 为什么队列容量为 8 时没有拒绝

任务总数为 10，两个工作线程先被占用，剩余 8 个任务恰好可以进入容量为 8 的队列，所以没有任务被拒绝。

### 6.3 LinkedBlockingQueue 的补充认识

`LinkedBlockingQueue` 默认构造方式通常使用接近 `Integer.MAX_VALUE` 的容量。它在一般负载下很难达到队列满的条件，因此线程池通常会持续排队，而不会扩展到 `maximumPoolSize`。

但这不代表 `maximumPoolSize` 或拒绝策略失效：当使用有界 `LinkedBlockingQueue` 且队列满时，线程池仍会尝试扩展到最大线程数；达到最大线程数后仍会执行拒绝策略。

## 7. 实验结论

1. 线程池不是提交一个任务就创建一个线程。工作线程数量受到 `corePoolSize` 和 `maximumPoolSize` 控制。
2. 达到核心线程数后，`ThreadPoolExecutor` 会优先尝试将新任务放入工作队列。
3. 队列容量决定了线程池在工作线程忙碌时可以暂存多少任务。
4. 当队列满且线程数达到最大值时，`AbortPolicy` 会拒绝新任务。
5. 增大队列容量可以减少短时间内的任务拒绝，但不能提高工作线程的实际处理能力。
6. 队列过大可能把即时拒绝转化为更长的排队等待和更大的内存占用，因此不能单纯通过增大队列来解决持续过载。

## 8. 工程应用思考

结合 OrderFlow 订单服务，假设后续增加异步任务（例如订单事件通知、审计记录或非关键后置处理），需要关注：

- 任务到达速率是否长期高于任务处理速率。
- 队列长度、队列等待时间和任务执行时间。
- 拒绝任务后如何处理：快速失败、降级、重试或持久化。
- 是否需要按业务重要性隔离线程池，避免非关键任务挤占订单核心流程资源。
- 是否需要设置队列容量上限、超时和告警阈值。

线程池参数应基于任务耗时、到达速率、可接受等待时间、内存预算和故障处理策略综合确定，而不是直接套用固定数值。
